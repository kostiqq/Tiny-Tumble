# Роадмап разработки Tiny Tumble (Unity)

*Черновик от 2026-10-06. 3D casual co-op arena brawler, сеттинг «арена на столе».*

Основа: GDD `design/gdd-tabletop-arena.md` (состав фич этапов 5–12 сверен с ним 2026-10-06) и брейншторм `design/coop-arena-brawl-ideas.md`. Мета и прогрессия, роли персонажей, режимы «волны / корона / доставка / предатель» в GDD отложены, поэтому в роадмапе они только в пострелизе.

Команда: Константин (лид-программист), программист №2, арт-директор / 3D, 2D UI-художник.

## 0. Стек и ключевые решения

| Задача | Выбор | Комментарий |
|---|---|---|
| Движок | Unity 6 LTS, URP | URP хватит для стилизованной графики, проще с производительностью |
| Сеть | **Netcode for GameObjects (NGO)**, P2P через хоста | Steam-транспорт для релиза, Unity Transport + Relay для разработки |
| DI | VContainer | Скоупы: Root → Scene → Match |
| Реактивность / события | **R3** + MessagePipe | R3 для реактивного состояния, MessagePipe для глобальных событий |
| Асинхронность | UniTask (добавить) | Нужна для Addressables, загрузки сцен, сетевых ожиданий; VContainer, R3 и MessagePipe с ней дружат |
| Контент | Addressables | Арены, персонажи, косметика, боссы, звук |
| Ввод | New Input System | `PlayerInputManager` для локального коопа до 4 геймпадов |
| Локализация | Unity Localization | RU + EN с первого UI |
| Онлайн-сервисы | Steamworks (Steamworks.NET, UPM-пакет `com.rlabrecque.steamworks.net`) | Инвайты, лобби, Remote Play Together; транспорт для NGO — Steam-транспорт на `SteamNetworkingSockets` под Steamworks.NET, Unity Relay как запасной вариант |
| CI / сборки | GameCI (GitHub Actions) | Автосборка Windows-билда на каждый merge в main |
| Контроль версий | Git + Git LFS | `.gitattributes` под Unity, Smart Merge для сцен и префабов |

### Решено (2026-10-06)

- **Сеть: Netcode for GameObjects, P2P через хоста.** Mirror не используется. Один из игроков — хост (он же сервер), остальные подключаются к нему; выделенных серверов нет. Связь между игроками идёт через Steam Networking (P2P с NAT-traversal и ретрансляцией Steam), на время разработки — Unity Relay.
- **Реактивность: R3** вместо UniRx (преемник от Cysharp, UniRx не развивается). В R3 нет `MessageBroker`, поэтому глобальные события — через **MessagePipe** (тоже Cysharp, интегрируется с VContainer).

### Сетевая модель (решение для всего проекта)

- **Одна ветка кода для всех режимов:** соло и локальный кооп тоже запускаются как host (NGO `StartHost` без подключений). Боты и локальные игроки — это «игроки» хоста. Так не нужно писать отдельную офлайн-логику.
- **Хост авторитетен** над физикой, правилами раунда, ботами и боссом.
- **Движение своего персонажа** — с предсказанием на клиенте (owner-driven), остальное интерполируется. Для толчков и бросков хост — источник истины, клиент показывает мгновенный локальный отклик (анимация, звук, VFX).
- Регулярно тестировать с симуляцией задержки 100–150 мс (Network Simulator в Unity Transport).
- **Два пути онлайна.** GDD описывает онлайн только через Steam Remote Play Together: игра идёт у хоста, а ввод друзей приходит как локальные геймпады. Это работает бесплатно поверх локального коопа, поэтому локальный кооп до 4 игроков должен быть безупречным с этапа 1. Сетевой P2P на NGO даёт настоящий онлайн без задержки видеопотока и остаётся в плане как решение команды.

## Этап 0. Пустой проект и инфраструктура

**Цель:** проект, который любой член команды клонирует, открывает и собирает одной командой.

- Создать проект Unity 6 LTS на URP, зафиксировать версию редактора.
- Git-репозиторий, `.gitignore` и `.gitattributes` под Unity, Git LFS для FBX/PNG/WAV/PSD, Unity Smart Merge (YAML merge).
- Правила веток: `main` всегда собирается, работа в фича-ветках через PR.
- Структура папок: `_Project/Scripts`, `Art`, `Audio`, `Prefabs`, `Scenes`, `Configs`, `AddressableAssets`; сторонние пакеты отдельно.
- Assembly Definitions: `Core`, `Infrastructure`, `Networking`, `Gameplay`, `AI`, `UI`, `Editor`, `Tests`. Зависимости только «вниз», это ускоряет компиляцию и держит архитектуру чистой.
- Установить пакеты: NGO, Unity Transport, Addressables, Input System, VContainer, R3, MessagePipe, UniTask, Localization, Cinemachine, Animation Rigging, Test Framework.
- Code style: `.editorconfig`, соглашения по именованию, короткий `CONTRIBUTING.md`.
- CI: GameCI собирает Windows-билд и прогоняет EditMode-тесты на каждый PR.
- Пайплайн для арта: масштаб (1 юнит = 1 м, персонаж-игрушка ~0.3–0.5 м или масштаб мира под персонажа), pivot, нейминг, экспорт FBX, референсная сцена для проверки моделей.

**Результат:** пустой проект в репозитории, зелёный CI, договорённости записаны.
**Параллельно:** арт-директор — стиль-скетчи, мудборд, тестовая модель персонажа; UI-художник — мудборд интерфейса.

## Этап 1. Архитектурный каркас

**Цель:** скелет, к которому подключаются все игровые системы.

- **Bootstrap-сцена** и единая точка входа. Поток: Boot → Main Menu → Lobby → Match → Results → Lobby.
- **VContainer LifetimeScopes:**
  - `RootLifetimeScope` (живёт всю игру): конфиги, сохранения, настройки, загрузка сцен, ввод, аудио, сеть, локализация.
  - `SceneLifetimeScope` для меню и лобби.
  - `MatchLifetimeScope` (создаётся на матч): правила раунда, арена, игроки, боты, счёт.
- **Конфиги** на ScriptableObject (параметры персонажа, толчков, режимов), регистрируются в DI.
- **Реактивное состояние и события:** R3 `ReactiveProperty` для состояния матча и UI, MessagePipe (через VContainer) для глобальных событий. Договориться, где что используется, чтобы не было «всё через события».
- **Addressables:** группы (Core, Arenas, Characters, Cosmetics, Bosses, Audio), labels, сервис загрузки с подсчётом ссылок и выгрузкой, загрузка сцен арен через Addressables.
- **Сервис сцен** на UniTask с экраном загрузки.
- **Ввод:** абстракция `IPlayerInput` (движение, прыжок, рывок, удар, захват/бросок, парирование, эмоция). Реализации: геймпад/клавиатура, бот, сетевой. Это ключ к тому, что боты и игроки управляют одним персонажем.
- **Локальный мультиплеер:** `PlayerInputManager`, присоединение по нажатию кнопки на геймпаде, разделение устройств.
- Сохранения и настройки (JSON, графика, звук, управление), логирование, debug-консоль / cheat-меню.

**Результат:** пустые сцены переключаются по полному игровому циклу, сервисы внедряются через DI, ассеты грузятся из Addressables.

## Этап 2. Сетевой фундамент

**Цель:** два клиента видят друг друга, а соло работает через тот же код.

- `NetworkManager` как сервис в `RootLifetimeScope`, обёртка `INetworkSession` (StartHost / StartClient / Shutdown, события подключения).
- **Внедрение зависимостей в сетевые объекты:** NGO создаёт объекты сам, поэтому нужен `INetworkPrefabInstanceHandler`, который инстанцирует префабы через VContainer (`IObjectResolver.Instantiate`), иначе `[Inject]` в `NetworkBehaviour` не сработает.
- **Addressables + NetworkPrefabs:** сетевые префабы должны быть зарегистрированы одинаково на хосте и клиентах до старта сессии. Загружать нужные группы Addressables до `StartHost/StartClient` и регистрировать префабы в рантайме.
- Синхронизация загрузки сцен (NGO SceneManagement или свой протокол «все загрузили арену → старт»).
- Модель игрока в сессии: `PlayerSlot` (сетевой клиент + индекс локального игрока + бот-флаг). Один сетевой клиент может иметь несколько локальных игроков.
- Лобби: хост, подключение по инвайту Steam (или код Relay на время разработки), готовность, выбор персонажа.
- Обработка отключений и переподключение: слот отвалившегося игрока держится, клиент возвращается сам. **Миграция хоста** (пересмотрено 2026-10-20): если хост ушёл или упал, преемник по заранее разосланному плану поднимает сессию с прежним составом, все возвращаются в лобби; идущий матч прерывается. Подробности — `networking.md`.
- Network Simulator: проверка при задержке и потерях пакетов.

**Результат:** хост + 1–3 клиента в одном лобби, переход в пустую арену, кубики-игроки двигаются синхронно.
**Транспорт (P2P):** Steam Networking для релиза (бесплатно, NAT-traversal и ретрансляция), Unity Relay для разработки и тестов. Выделенных серверов нет: при уходе хоста текущий матч прерывается, а сессия продолжается у преемника (миграция в лобби).

## Этап 3. Персонаж: движение, физика, анимация

**Цель:** персонажем приятно управлять, он смешно падает.

- Физический контроллер на Rigidbody: движение, ускорение, прыжок, контроль в воздухе, проверка земли, склоны, движущиеся платформы (вращающиеся и наклоняемые арены этого требуют с первого дня).
- Сетевая синхронизация движения: предсказание у владельца, интерполяция у остальных, коррекция хостом.
- **Ragdoll с быстрым подъёмом:** активный ragdoll или переключение animator ↔ ragdoll с blend-возвратом. Ограничение длительности, чтобы не раздражало.
- **«Желейная» анимация:** процедурный wobble (пружинные кости / Animation Rigging), один базовый риг, небольшой набор клипов.
- Камера: общая камера для всех игроков на арене (Cinemachine Target Group), без сплит-скрина.
- Конфиги чувствительности, геймпад как основной контроллер.

**Результат:** серые капсулы на серой арене бегают, прыгают, падают и встают, локально и по сети.
**Параллельно:** арт-директор — финальный базовый риг и модель персонажа, первые анимации.

**Статус (2026-10-24): код этапа готов.** Капсула на Rigidbody с опорой, склонами, движущимися опорами, «койот-временем» и буфером прыжка; предсказание у владельца с плавной коррекцией и интерполяция чужих; ragdoll с быстрым подъёмом; «желе» на пружинах; общая камера Cinemachine Target Group; конфиг чувствительности стика. Риг, клипы и ragdoll на костях подключатся после модели (точки подключения описаны). Подробности — `character-and-combat.md`.

## Этап 4. Боевые механики

**Цель:** ядро геймплея — выталкивание с арены.

- **Модель толчка без HP:** процент «встряска» (GDD: толчок +10%, бросок предметом +15%, бросок игроком +20%), увеличивает дальность отлёта. Kill-зоны за краем арены, респаун или выбывание по правилам режима.
- Удар / толчок: хитбоксы, окна активности, кулдауны.
- **Захват и бросок** предметов и игроков; переноска союзника; цепочка захвата (двое держат одного).
- **Парирование** таймингом с отбрасыванием атакующего.
- **Рывок** с перезарядкой.
- **Эмоция-кнопка.**
- Сетевая модель боя: хост решает попадания; клиент мгновенно показывает анимацию/VFX/звук; захваты синхронизируются через `NetworkObject` parenting или физические соединения на хосте.
- Хит-стоп, тряска камеры, частицы — «сочность» с самого начала, без неё прототип не оценить.
- Физические предметы на арене (подбираемые и бросаемые) как общий компонент.

**Статус (2026-10-24): код этапа готов.** Встряск и отлёт, kill-зона, выбывание или возрождение; толчок с окнами; захват и бросок предметов и игроков с зарядкой, переноска, цепочка захвата; парирование; рывок; эмоции; хит-стоп, тряска камеры, частицы; предметы на арене; простые боты-драчуны. Всё работает в соло, локально и по сети (сквозной автотест на двух сборках). Осталось: звук и обязательный плейтест вехи A с подбором чисел в конфигах. Подробности — `character-and-combat.md`.

**── Веха A: играбельный прототип.** 2–4 игрока (локально и по сети) плюс простые боты выталкивают друг друга на 1 серой арене. **Обязательный плейтест:** если в это не весело играть, править механики до перехода дальше.

## Этап 5. Фреймворк арен и опасностей

**Цель:** арены собираются из модулей без программиста.

- Описание арены: Addressable-сцена + `ArenaDefinition` (комната, точки спауна, границы стола, kill-зоны, набор опасностей, предметы для броска, несовместимые модификаторы, превью для UI).
- **Модули опасностей (из GDD, раздел 9):** вращение, наклон / крен, разрушаемые плитки, жидкость (выбывание), жар (подбрасывание + рост встряска), липкая и скользкая зоны, ветер, движущийся пол, падающие предметы с тенью-предупреждением, подбрасывающая поверхность. Каждый — компонент с конфигом и сетевой синхронизацией. Эти же модули используют атаки ведущих (этап 8).
- **Предметы для броска:** 4–8 на арене, общий компонент из этапа 4, наборы по комнатам (масло, горошины, ягоды, пешки, кубики…).
- **События окружения:** раз в 30–45 сек с предупреждением за 2 сек; свои у арены плюс общие для комнаты (падает ложка, разливается кофе, кот сносит часть арены, ластик стирает мостик). В режиме против босса отключаются.
- Сетевая синхронизация движущихся арен (детерминированная по сетевому времени, а не по физике, чтобы не рассинхронизировались).
- Камера без движения: арена целиком в одном экране.
- Редакторные инструменты: валидатор арены, гизмо для спаунов и kill-зон.
- **Первая четвёрка арен (грейбокс → арт):** Сковородка (жар), Торт на подставке (вращение), Крышка в супе (крен + жидкость), Шахматная доска (движущиеся препятствия). Они покрывают обе комнаты.

**Результат:** арт-директор собирает арену из готовых модулей.

## Этап 6. Игровые режимы, раунды и модификаторы

**Цель:** полноценный матч с правилами.

- **Цикл матча (GDD, раздел 3):** лобби → выбор режима (только допустимые для числа игроков) → выбор арены (конкретная, случайная или плейлист комнаты) → заставка ведущего 2–3 сек → объявление модификатора → раунд → табло и повтор → голосование → … → итог после 3–5 раундов → «ещё раз» одной кнопкой с тем же составом.
- **Фреймворк режимов:** машина состояний матча, `IGameMode` с условиями победы, правилами возвращения и счёта.
- **Last One Standing:** до 3 очков; с 90-й секунды края стола сужаются к центру; ведущий не атакует, а запускает события окружения; выбывший кидается крошками с края стола (слабый толчок).
- **Команды:** состав по таблице GDD (раздел 6) для 1–4 игроков, автодобор ботов до равных команд с переопределением в лобби, дружественный толчок включён, цвет обводки + флажок команды.
- **Модификаторы (10 штук):** низкая гравитация, скользкий пол, гиганты, крошки, только броски, вращающаяся арена, горячая картошка, туман, зеркальное управление (10 сек), наклон арены. Система должна уметь включать модификатор **на весь раунд** (PvP) и **по таймеру по команде ведущего** (босс-режим) — один код на оба случая.
- **Голосование:** 3 случайных варианта, 5 сек, ничья → случайный; без повтора два раунда подряд; автоисключение несовместимых с ареной; в лобби — «без модификаторов» и отключение отдельных.
- Счёт и таблица результатов; сбор статистики матча (нужна повтору и будущим наградам из меты).
- Все стартовые числа (встряск, окна, длительности) — в конфигах, их меняет плейтест.

## Этап 7. ИИ ботов

**Цель:** любой режим играбелен в одиночку. По GDD это ключевая задача прототипа, поэтому простой бот (подойти и толкнуть, держаться от края) появляется уже на Вехе A, а здесь доводится.

- Бот управляет персонажем через тот же `IPlayerInput`, что и игрок, работает только на хосте.
- Архитектура: Utility AI с приоритетами из GDD: отойти от края и опасности → увернуться от телеграфированной атаки → схватить ближайший предмет → идти к врагу и толкать/бросать к краю.
- Навигация: стирринг + проверка края лучами + знание о модулях опасностей (NavMesh плохо работает на вращающихся и разрушаемых аренах).
- **Сложность (GDD):** Лёгкий — реакция 0,6 сек, не парирует, иногда падает сам; Нормальный — 0,35 сек, парирует в 30%; Сложный — 0,2 сек, парирует в 60%, использует модификаторы.
- **Бот-напарник против босса:** целится в слабое место, подбегает для захвата-цепочки, даёт себя бросить.
- Боты заполняют пустые слоты и заменяют отключившихся; гость с геймпадом заменяет бота со следующего раунда.
- Тестовые конфигурации 1, 2 и 4 игрока для каждого режима и босса.

## Этап 8. Босс-ведущий и режим «против босса»

Это лицо игры по GDD, поэтому Кот входит в вертикальный срез.

- **Фреймворк ведущего:** конечный автомат (выбор цели → атака из набора фазы → пауза; модификатор по таймеру). Один каркас кода, три набора данных.
- **Шкала «терпения»** вместо HP: снижается от бросков предметов и напарников в подсвеченное слабое место, парирований атак, удержания лапы захватом-цепочкой.
- **3 фазы:** каждая добавляет атаку и переносит слабое место; сценка 2 сек на смене фазы.
- **Смена правил каждые 20–30 сек** (в фазе 3 — 15 сек) через систему модификаторов этапа 6, с объявлением за 2 сек.
- **Телеграфирование** каждой атаки минимум за 1 сек: тень, замах, звук.
- **Масштабирование:** терпение 40/65/85/100% при 1/2/3/4 игроках; соло — атаки на 25% медленнее, слабое место без захвата-цепочки; бот-напарник = половина игрока.
- **Режим:** 1–4 игрока + боты; возвращение через 5 сек на «парашюте-салфетке»; запас 3 возвращения на игрока; поражение — все вне стола или запас исчерпан. Бой 4–6 минут.
- **Модель ведущего частичная:** лапы/руки и лицо на фоне (дешевле полной модели).
- **Порядок:** Кот целиком (шлепок, смахивание половины стола, прыжок на стол) → Повар → Робот-пылесос.

**── Веха B: вертикальный срез.** 1 базовый персонаж + 6–8 вариантов, 4 арены первой четвёрки в финальном арте, Last One Standing + Команды + **бой с Котом**, все 10 модификаторов с голосованием, боты трёх уровней, локальный кооп, Remote Play Together и P2P-онлайн, базовое меню. Это то, что показывают в трейлере и потенциальным партнёрам.

## Этап 9. UI/UX и фронтенд

UI-художник работает над этим параллельно с этапа 3; здесь — интеграция и полировка.

## Этап 10. Соло-кампания «Шоу»

- **Структура (GDD, раздел 10):** 27 испытаний в 3 главах по ведущему (Кот на кухне / Кухня шефа / Уборка в детской), 8 испытаний + босс в каждой.
- Испытания открываются по одному; босс главы — при 12 звёздах из 24.
- **Типы испытаний:** выживание, выталкивание с условием, парирование, кооп с ботом, модификатор, мини-босс, босс главы. Каждый тип — шаблон с параметрами, сами испытания — данные (ScriptableObject).
- **Звёзды:** 1 — выполнить; 2 — по времени или без падений; 3 — доп. условие.
- **Туториал:** первые 3 испытания главы 1 вводят по одной механике с подсказкой на экране (отдельной песочницы нет).
- Комментарии ведущего к каждому испытанию.
- Кампанию можно проходить вдвоём на одном экране: второй игрок заменяет бота-напарника.
- Сохранение прогресса кампании.

## Главные технические риски

1. **Сетевая физика.** Физические толчки и броски по сети — самое сложное в проекте. Снижение риска: хост-авторитет, предсказание только своего движения, ранний тест с задержкой (этап 2–4).
2. **ИИ на динамичных аренах.** Без NavMesh, на стирринге и знании об опасностях; простой бот уже на Вехе A, доводка до Вехи B.
3. **Связка NGO + VContainer + Addressables.** Нестандартная: инъекция в сетевые объекты и регистрация сетевых префабов из Addressables решаются на этапе 2, до основного кода.
4. **«Весело ли это».** Проверяется на Вехе A, до вложений в контент.
