# Сеть: как устроено и как проверять

*Этап 2 роадмапа, 2026-10-20. Дополняет раздел «Сетевая модель» в `development-roadmap.md` и раздел 7 `CONTRIBUTING.md`.*

## Коротко

- **Всё идёт через сессию NGO.** Соло и локальный кооп — это хост без подключений. Отдельной офлайн-логики нет.
- **Хост авторитетен.** Хост симулирует всех персонажей и решает бой. Клиент каждый тик отправляет хосту свой ввод и сразу предсказывает по нему своё движение; положения всех приходят снимками хоста. Чужих персонажей клиент интерполирует с задержкой 0.1 с. Подробности — `character-and-combat.md`, раздел «Сеть» (этап 3).
- **Транспорт сейчас — Unity Transport по IP** (порт 7777 в `Configs/SessionConfig`). Relay и Steam подключатся позже через настройку транспорта в `NetworkSession`; игровой код их не заметит.
- **Сцены NGO не используются** (`EnableSceneManagement = false`), потому что арены — это сцены Addressables. Хост объявляет переход, клиенты грузят ту же сцену сами, а матч стартует, когда арену загрузили все.

## Поток игры

```
Меню ──«Играть»──► StartHost ──► Лобби (хост)
Меню ──«Подключиться» IP──► StartClient ──► клиент получает объект сессии ──► идёт за хостом в Лобби

Лобби: клиенты жмут «Готов» ──► хост «Начать матч» ──► хост объявляет Match (эпоха N)
  ├─ хост грузит Match + арену, ждёт отчёты «загрузил N» от всех клиентов (таймаут — кик)
  └─ клиенты грузят Match + арену, отправляют «загрузил N»
Хост спавнит персонажей по слотам (владелец — клиент слота) и ботов (владелец — хост)

Конец матча (хост): Despawn всех персонажей → выгрузка арены → Results → клиенты идут следом
«В меню» у клиента: Shutdown его сессии. Хост ушёл или упал — миграция (см. ниже).
```

## Обрывы связи и миграция хоста

*Добавлено 2026-10-20. Пересматривает решение роадмапа «миграции хоста нет».*

**Игрок узнаётся по ключу, а не по сетевому id.** Ключ (`PlayerIdentity`) — случайное 64-битное число на запуск игры, клиент отправляет его при подключении. Слот P1–P4 принадлежит ключу. Сетевой id NGO меняется при каждом подключении, поэтому для узнавания не годится. Со Steam ключом станет SteamID.

**Клиент отвалился (хост на месте).**
- Хост замечает обрыв через `DisconnectTimeout` (5 с). Слот и цвет игрока остаются за ним `ReservedSlotTimeout` (60 с). В лобби такой слот подписан «связь потеряна, ждём возвращения». Начать матч он не мешает: в матч отключённый игрок просто не попадёт.
- Клиент сам пытается вернуться к тому же хосту `ReconnectWindow` (10 с); всё это время на экране «Связь с хостом потеряна. Переподключаемся…».
- Вернувшегося хост пускает даже посреди матча и при полном лобби. Игрок досматривает матч зрителем: своего персонажа у него в этом раунде нет, его персонаж выбыл при обрыве. После матча он идёт со всеми в лобби в свой прежний слот.
- Объекты матча хост показывает клиенту только после того, как тот загрузил арену (`CheckObjectVisibility` + `NetworkShow`). Иначе NGO создал бы их в чужой сцене, и при смене сцены клиент уничтожил бы сетевые объекты сам — это ошибка NGO.

**Хост ушёл или упал.**
- Хост держит в объекте сессии *план миграции*: подключённые клиенты по номеру слота (P2 раньше P3), их адреса (как их видит хост) и порты, на которых каждый поднимет хост. План рассылается всем при любом изменении состава.
- Уходя штатно (в меню), хост рассылает «ухожу», и клиенты сразу переходят к плану. Если хост упал, клиенты замечают это через `DisconnectTimeout`, затем `ReconnectWindow` секунд пробуют вернуться к нему (обрыв мог быть у самого клиента) и только потом переходят к плану.
- По плану: первый кандидат поднимает хост с прежним составом и меткой сессии; остальные подключаются к нему. Если кандидат не отвечает `MigrationConnectTimeout` секунд, роль берёт следующий. Список у всех одинаковый, договариваться не нужно.
- Все оказываются в лобби: идущий матч прерывается, слоты и цвета сохраняются. Слот ушедшего хоста зарезервирован: вернувшись, он займёт его уже как клиент.
- Метка сессии (`SessionToken`) не даёт клиенту присоединиться к посторонней игре, случайно оказавшейся по адресу преемника.

**Ограничения:**
- Через интернет по прямому IP миграция обычно не сработает: преемник за NAT без проброса порта недоступен остальным. В LAN и на одной машине всё работает. С транспортом Steam это решается: адресом будет SteamID, а связь пойдёт через ретрансляцию Steam.
- Если пропала сеть у самого первого кандидата, а хост жив, кандидат через `DisconnectTimeout + ReconnectWindow` поднимет свою сессию и останется в ней один. Остальные продолжат со старым хостом, его слот там будет в резерве. Чтобы вернуться, игроку нужно выйти в меню и подключиться заново.
- Перед миграцией клиенты ждут `DisconnectTimeout + ReconnectWindow` (≈15 с), если хост упал без предупреждения. Это цена защиты от ложной миграции при собственном обрыве клиента; окно настраивается в `SessionConfig`.
- Состояние матча не переносится: только состав лобби.

## Где что лежит

| Что | Где |
|---|---|
| Интерфейсы для игры и UI: `INetworkSession`, `ILobby`, `ISessionLauncher`, коды `DisconnectReasons` | `Core/Network` |
| NetworkManager: создаётся отдельным корневым объектом из `Prefabs/NetworkManager.prefab` (NGO не разрешает его вкладывать) | `Networking/Session/NetworkRuntime` |
| Старт хоста и клиента, одобрение подключений (версия протокола, свободные слоты, «только в лобби»), отключения | `Networking/Session/NetworkSession`, `ConnectionPayload` |
| DI в сетевые объекты: NGO создаёт объекты на клиентах через `InjectingPrefabHandler` → `IObjectResolver.Instantiate` текущего скоупа. Скоуп кладёт себя в стек через `NetworkResolverScope` | `Networking/Spawning` |
| Сетевые префабы из Addressables: всё с меткой `network` грузится и регистрируется **до** StartHost/StartClient (`ForceSamePrefabs`) | `Networking/Spawning/NetworkPrefabRegistry` |
| Объект сессии (`Net_Session`): слоты P1..P4 + состояние хоста в `NetworkVariable`, RPC «дай слот», «готов», «загрузил». Переживает смену сцен | `Networking/Lobby/SessionNetworkState`, `SessionLobby`, `SlotTable` |
| Переходы между сценами с учётом сессии: клиент идёт за хостом, «в меню» закрывает сессию | `Networking/Flow/NetworkGameFlow` (зарегистрирован как `IGameFlow`) |
| Ввод удалённого игрока: владелец каждый тик шлёт кадр с номером (ненадёжно, по три последних кадра в пакете), на хосте это обычный `IPlayerInput` с очередью | `Networking/Input/NetworkPlayerInput`, `RemoteInputQueue` |
| Снимки состояния тел, интерполяция, история и коррекция предсказания (без правил игры) | `Networking/Sync` |
| Персонаж: симулирует хост; владелец предсказывает своё движение, остальные интерполируют | `Gameplay/Characters/PlayerCharacter`, `CharacterNetSync` |

**`PlayerSlot`** = сетевой клиент + индекс локального игрока на нём. Один клиент может занимать несколько слотов (кооп на одном экране по сети). Слот задаёт номер игрока и цвет.

## Правила для нового сетевого кода

- Новый сетевой префаб: компонент `NetworkObject`, группа Addressables своего слоя, **метка `network`**. Ссылаться на него из `NetworkManager` не нужно.
- `[Inject]` в `NetworkBehaviour` работает, если объект создан через DI: на хосте — `IObjectResolver.Instantiate`, на клиентах это делает обработчик префабов.
- `NetworkVariable` пишите в `OnNetworkSpawn` (на сервере) или позже. До `Spawn` NGO выдаёт предупреждение. Начальные значения передавайте обычными полями, как `StubCharacter.ConfigureServer`.
- Перед сменой сцены хост **деспавнит** сетевые объекты этой сцены. Если клиент уничтожит заспавненный объект вместе со сценой сам, NGO запишет ошибку.
- Обработчики событий, которые вызываются из сетевых колбэков, не должны бросать исключения: исключение прервёт применение остального сообщения NGO. `SessionLobby` изолирует подписчиков, но UI всё равно отписывается в `OnDisable`/`OnDestroy`.
- UI, который виден только хосту или только клиенту, переключает `SessionRoleVisibility` на всегда активном корне UI. Не вешайте его на саму кнопку: Unity не вызовет `OnDestroy` у объекта, который ни разу не был активен.

## Как проверить руками

1. **Tiny Tumble → Build → Windows Development** (сборка в `Builds/Dev`, папка в `.gitignore`).
2. Запустите два экземпляра `TinyTumble.exe` (или сборку + редактор).
3. В первом: «Играть». Во втором: адрес `127.0.0.1` (или LAN-IP хоста) → «Подключиться».
4. Во втором «Готов», в первом «Начать матч». Управление — таблица в `character-and-combat.md`.

Консоль (` или F1):

| Команда | Что делает |
|---|---|
| `net.host` | создать игру и перейти в лобби |
| `net.join 192.168.0.10[:7777]` | подключиться |
| `net.leave` | выйти в меню (закрывает сессию) |
| `net.status` | роль, id, состояние хоста, слоты, симулятор |
| `net.sim 60 10 2` | задержка 60 мс, джиттер 10 мс, потери 2% на отправку с этой машины; `net.sim off` |
| `net.drop 8` | полностью оборвать связь этой машины на 8 с (обе стороны). Проверка переподключения и миграции руками |

Задержка симулятора добавляется на отправку **каждой** стороной: `net.sim 60` у обоих даёт RTT около 120 мс. Симулятор работает в редакторе и development-сборках.

## Сквозной автотест (две сборки)

Хост и клиент проходят меню → лобби → матч → итоги → лобби с виртуальной клавиатурой: клиент жмёт W, хост — D. Каждая сторона проверяет, что двигаются и свой персонаж (у клиента — предсказанный), и чужой (интерполированный). В матче есть бот, он дерётся по-настоящему; чтобы исход драки не заканчивал матч посреди проверки сети, в автотесте выпавшие всегда возрождаются. Итог — строка `[AutoTest] RESULT PASS|FAIL` в логе и код выхода 0/1.

```bash
EXE=Builds/Dev/TinyTumble.exe
$EXE -batchmode -nographics -tt-autotest host   -tt-clients 1 -logFile host.log &
$EXE -batchmode -nographics -tt-autotest client -tt-address 127.0.0.1 -logFile client.log
```

Ключи (общие для всех копий):

| Ключ | Что делает |
|---|---|
| `-tt-clients 2` | сколько клиентов в сессии; передаётся и хосту, и клиентам |
| `-tt-port 7778` | порт, на котором эта копия поднимет хост, если станет преемником. **У копий на одной машине порты должны различаться** |
| `-tt-netsim 60,10,2` | симулятор сети |
| `-tt-bots 0` | сколько ботов в матче (по умолчанию из `MatchConfig`) |
| `-tt-duration 6` | длительность матча в сценарии `full` |
| `-tt-scenario full` | по умолчанию: цикл с проверкой движения своего и чужого кубика |
| `-tt-scenario hostleave` | хост выходит в меню посреди матча; клиент становится новым хостом и сохраняет свой слот |
| `-tt-scenario hostcrash` | процесс хоста убит посреди матча (нужно 2+ клиента); первый по плану становится хостом, остальные переходят к нему, у всех прежние слоты |
| `-tt-scenario clientdrop` | у клиента на 8 с пропадает сеть посреди матча; он возвращается, досматривает матч и попадает в лобби в свой слот |

Пример `hostcrash` на одной машине:

```bash
$EXE -batchmode -nographics -tt-autotest host   -tt-clients 2 -tt-scenario hostcrash -logFile host.log &
$EXE -batchmode -nographics -tt-autotest client -tt-clients 2 -tt-scenario hostcrash -tt-port 7778 -logFile c1.log &
$EXE -batchmode -nographics -tt-autotest client -tt-clients 2 -tt-scenario hostcrash -tt-port 7779 -logFile c2.log
```

Проверено 2026-10-20 и повторно 2026-10-24 (после этапов 3–4): проходят `full` (в том числе с симулятором 60/10/2), `hostleave`, `hostcrash` (хост + 2 клиента) и `clientdrop`; в логах нет предупреждений NGO.

## Что ещё не сделано по этапу 2

- **Steam:** транспорт `SteamNetworkingSockets` и инвайты. В проекте стоит Steamworks.NET (`com.rlabrecque.steamworks.net`), а не Facepunch, как записано в роадмапе. Транспорт для NGO нужно брать под Steamworks.NET.
- **Unity Relay** для игры через интернет без проброса портов (нужны пакет `com.unity.services.multiplayer` и привязка проекта к Unity Cloud).
- **Выбор персонажа в лобби**: пока у всех кубик-заглушка.
- **Возврат в идущий матч** с новым персонажем: сейчас вернувшийся досматривает матч зрителем. Зависит от правил раундов (этап 6).
- Тексты причин отключения (`UI/Session/DisconnectReasonTexts`) пока строками в коде; перейдут в Unity Localization вместе с остальным UI.
