# Сеть: как устроено и как проверять

*Этап 2 роадмапа, 2026-10-20. Дополняет раздел «Сетевая модель» в `development-roadmap.md` и раздел 7 `CONTRIBUTING.md`.*

## Коротко

- **Всё идёт через сессию NGO.** Соло и локальный кооп — это хост без подключений. Отдельной офлайн-логики нет.
- **Хост авторитетен.** Хост симулирует всех персонажей и решает бой. Клиент каждый тик отправляет хосту свой ввод и сразу предсказывает по нему своё движение; положения всех приходят снимками хоста. Чужих персонажей клиент интерполирует с задержкой 0.1 с. Подробности — `character-and-combat.md`, раздел «Сеть» (этап 3).
- **Два транспорта: Steam и прямой IP.** Адрес хоста везде — `SessionEndpoint` (тип + 64-битное значение + порт: IP:порт или SteamID, позже код Relay). Настройку NGO под тип адреса делает `ISessionTransport`: `SessionTransports` выбирает между `DirectIpTransport` (Unity Transport, порт 7777 из `Configs/SessionConfig`) и `SteamSessionTransport` (свой транспорт NGO `SteamNetworkTransport` на `SteamNetworkingSockets`, P2P по SteamID через ретрансляцию Steam, без проброса портов). Клиент идёт тем транспортом, на который указывает адрес; новый хост поднимается через Steam, если Steam запущен, иначе по IP (`net.host ip|steam` меняет это). Игровой код транспорта не видит.
- **Steam пока на App ID 480 (Spacewar)** из `steam_appid.txt` в корне проекта; development-сборка кладёт его рядом с exe. Без запущенного Steam всё работает по IP.
- **Пати отдельно от сессии.** Пати — игроки, которые держатся вместе и переезжают между сессиями целиком; у неё есть id и лидер. В одной сессии может быть несколько пати. Подробности — раздел «Пати» ниже.
- **Поиск игры.** Лидер пати ищет открытое лобби с местами на всю пати и подходящим пингом и уводит туда пати; не нашёл — открывает своё лобби и ждёт; время вышло — матч, пустые места занимают боты. Подробности — раздел «Поиск игры» ниже.
- **Сцены NGO не используются** (`EnableSceneManagement = false`), потому что арены — это сцены Addressables. Хост объявляет переход, клиенты грузят ту же сцену сами, а матч стартует, когда арену загрузили все.

## Поток игры

```
Меню ──«Играть»──► StartHost ──► Лобби (хост)
Меню ──«Подключиться» IP──► StartClient ──► клиент получает объект сессии ──► идёт за хостом в Лобби

Лобби: клиенты жмут «Готов» ──► хост «Начать матч» ──► хост объявляет Match (эпоха N)
  ├─ хост грузит Match + арену, ждёт отчёты «загрузил N» от всех клиентов (таймаут — кик)
  └─ клиенты грузят Match + арену, отправляют «загрузил N»
Хост спавнит персонажей по слотам (владелец — клиент слота) и ботов (владелец — хост)

Конец матча (хост): Despawn всех персонажей → выгрузка арены → Results → клиенты идут следом
«В меню» у клиента: Shutdown его сессии. Хост ушёл или упал — миграция (см. ниже).
```

## Обрывы связи и миграция хоста

*Добавлено 2026-10-20. Пересматривает решение роадмапа «миграции хоста нет».*

**Игрок узнаётся по ключу, а не по сетевому id.** Ключ (`PlayerIdentity`) — случайное 64-битное число на запуск игры, клиент отправляет его при подключении. Слот P1–P4 принадлежит ключу. Сетевой id NGO меняется при каждом подключении, поэтому для узнавания не годится. Со Steam ключом станет SteamID.

**Клиент отвалился (хост на месте).**
- Хост замечает обрыв через `DisconnectTimeout` (5 с). Слот и цвет игрока остаются за ним `ReservedSlotTimeout` (60 с). В лобби такой слот подписан «связь потеряна, ждём возвращения». Начать матч он не мешает: в матч отключённый игрок просто не попадёт.
- Клиент сам пытается вернуться к тому же хосту `ReconnectWindow` (10 с); всё это время на экране «Связь с хостом потеряна. Переподключаемся…».
- Вернувшегося хост пускает даже посреди матча и при полном лобби. Игрок досматривает матч зрителем: своего персонажа у него в этом раунде нет, его персонаж выбыл при обрыве. После матча он идёт со всеми в лобби в свой прежний слот.
- Объекты матча хост показывает клиенту только после того, как тот загрузил арену (`CheckObjectVisibility` + `NetworkShow`). Иначе NGO создал бы их в чужой сцене, и при смене сцены клиент уничтожил бы сетевые объекты сам — это ошибка NGO.

**Хост ушёл или упал.**
- Хост держит в объекте сессии *план миграции*: подключённые клиенты по номеру слота (P2 раньше P3) и адрес (`SessionEndpoint`), по которому каждый будет доступен, став хостом. Клиент сообщает его о себе сам в запросе на подключение (`ConnectionPayload.Successor`), хост проверяет через транспорт (`ISessionTransport.GetSuccessorEndpoint`): для IP клиент шлёт только порт, а IP хост берёт из соединения; для Steam клиент шлёт свой SteamID, и хост верит ему, только если с этого SteamID к нему действительно подключены. Преемник поднимает хост тем же транспортом, через который шла сессия. План рассылается всем при любом изменении состава.
- Клиент, до которого хост не смог вычислить адрес, в план не входит: иначе он поднял бы свой хост, а остальные пропустили бы его, и сессия раскололась бы надвое. При миграции такой клиент только подключается к преемнику.
- Уходя штатно (в меню), хост рассылает «ухожу», и клиенты сразу переходят к плану. Если хост упал, клиенты замечают это через `DisconnectTimeout`, затем `ReconnectWindow` секунд пробуют вернуться к нему (обрыв мог быть у самого клиента) и только потом переходят к плану.
- По плану: первый кандидат поднимает хост с прежним составом и меткой сессии; остальные подключаются к нему. Если кандидат не отвечает `MigrationConnectTimeout` секунд, роль берёт следующий. Список у всех одинаковый, договариваться не нужно.
- Все оказываются в лобби: идущий матч прерывается, слоты и цвета сохраняются. Слот ушедшего хоста зарезервирован: вернувшись, он займёт его уже как клиент.
- Метка сессии (`SessionToken`) не даёт клиенту присоединиться к посторонней игре, случайно оказавшейся по адресу преемника.

**Ограничения:**
- Через интернет по прямому IP миграция обычно не сработает: преемник за NAT без проброса порта недоступен остальным. В LAN и на одной машине всё работает. Через Steam адрес преемника — SteamID, связь идёт через ретрансляцию Steam, поэтому NAT не мешает.
- Через Steam установка соединения может занимать несколько секунд (поиск маршрута через ретрансляцию). Поэтому к преемнику через Steam идёт одна попытка на всё окно `MigrationConnectTimeout` (6 с), а не короткие попытки по 3 с, как по IP. Если на плейтесте миграция через Steam будет срываться по таймауту, первым делом увеличить `MigrationConnectTimeout` и `ReconnectWindow`.
- Если пропала сеть у самого первого кандидата, а хост жив, кандидат через `DisconnectTimeout + ReconnectWindow` поднимет свою сессию и останется в ней один. Остальные продолжат со старым хостом, его слот там будет в резерве. Чтобы вернуться, игроку нужно выйти в меню и подключиться заново.
- Перед миграцией клиенты ждут `DisconnectTimeout + ReconnectWindow` (≈15 с), если хост упал без предупреждения. Это цена защиты от ложной миграции при собственном обрыве клиента; окно настраивается в `SessionConfig`.
- Состояние матча не переносится: только состав лобби.

## Пати

*Добавлено 2026-11-13 (шаг 3 плана «Пати и матчмейкинг»).*

**Что это.** Пати — игроки, которые держатся вместе. У каждого слота в `SlotTable` есть `PartyId` и метка лидера пати, поэтому состав пати видят все, а миграция хоста переносит его вместе со слотами. В одной сессии может быть несколько пати: своя у хоста и пришедшие к нему. Лидер у пати один, и он решает, куда пати переезжает.

**Кто в какой пати.**
- «Играть» из меню — новая пати, мы её лидер.
- Друг, подключившийся из меню, по приглашению или по адресу, вступает в пати хоста (в запросе на подключение `PartyId = 0`).
- Клиент, пришедший со своей пати (переезд), остаётся в ней, и лидер у неё прежний.
- Лидер отключился — пати ведёт следующий по слоту подключённый участник. Ушёл хост, который вёл пати, — её ведёт новый хост, если он в этой пати. Правило одно у всех, договариваться не нужно (`SlotTable.ElectLeader`).
- Пока машина в сессии, своя пати берётся из своих слотов (`PartyState.Adopt`); между сессиями (переезд, восстановление) она хранится в `PartyState` и уходит хосту в запросе на подключение.

**Допуск пати целиком.** В `ConnectionPayload` есть `PartyId`, размер всей пати в слотах и флаг лидера. Первый участник чужой пати проходит, только если в лобби есть места на всю пати; иначе отказ `party_too_big`. Дальше хост держит эти места для остальных участников, пока они не подключатся или не выйдет `2 × ConnectTimeout`. Посторонние в эти места не попадут (`ConnectionAdmission.Evaluate`).

**Переезд.** Лидер командует, переехать можно только из лобби:
1. Хост рассылает команду всем клиентам: id пати, куда ехать, размер пати и адрес, где лидер поднимет хост, если пати придётся собираться у него. Команда может обогнать обновление слотов (лидер скомандовал сразу после входа друга); тогда клиент без своего слота откладывает её до прихода состава.
2. Каждый участник сам закрывает свою сессию и подключается к новому хосту со своей пати. Сцена лобби остаётся, меняется только сессия под ней; поверх висит экран «Переезжаем вместе с пати…».
3. Новый хост не принял пати или недоступен — пати собирается у лидера. Лидер поднимает свою сессию тем же транспортом, остальные подключаются к нему.
4. Старый хост освобождает слоты уехавших сразу, без резерва на 60 с. Если уезжает пати самого хоста, остальные игроки сессии переходят к преемнику, как при уходе хоста; уезжающие в план миграции не входят.

«Уйти к себе» (`IParty.Regroup`) — тот же переезд без цели: пати уходит из чужой сессии к лидеру. Лидер, принявший приглашение Steam посреди своей сессии, уводит туда всю пати. Участник (не лидер) по приглашению не уходит: сначала выйти в меню.

**Ограничения:**
- Адрес цели переезда по IP должен быть доступен всем участникам: `127.0.0.1` годится только для копий на одной машине.
- После переезда через Steam в лобби Steam нового хоста входит только лидер (он принимал приглашение); у остальных участников кнопки «Пригласить» нет. Состав и слоты это не затрагивает.
- Если часть пати подключилась к новому хосту, а часть нет, неподключившиеся пойдут к лидеру и, не найдя его хостом, вернутся в меню. На одной машине такой случай не воспроизводится; проверить на плейтесте.

## Поиск игры

*Добавлено 2026-11-13 (шаг 4 плана «Пати и матчмейкинг»).*

**Кто ищет.** «Найти игру» (`IMatchmaking.StartSearch`) можно из главного меню (тогда сначала поднимается своё лобби с пати из одного себя) или лидером пати, который хостит лобби, где только его пати. Поиск ведёт лидер; остальные видят таймер (`IMatchmaking.SecondsLeft`) — он лежит в объекте сессии (`MatchmakingInfo`) и одинаков у всех.

**Как ищет** (`Networking/Matchmaking/MatchmakingService`):
1. Ищет открытые лобби: та же версия протокола, свободных мест не меньше, чем слотов у пати. Первые `CloseSearchSeconds` (15 с) — только ближние (фильтр расстояния Steam «близко»), потом — «по умолчанию»; «далеко» и «по всему миру» не используются.
2. Отбрасывает лобби с оценкой пинга выше `MaxEstimatedPingMs` (120 мс RTT). Если оценки нет, лобби допускается, но проигрывает лобби с известным пингом.
3. Выбирает лучшее: больше игроков, ниже пинг, меньше ключ (`MatchmakingRules.TryPick`) — и уводит туда пати переездом с пометкой «нашли поиском». Хост отказал или недоступен — пати собирается у лидера, лобби попадает в исключения, поиск идёт дальше.
4. Не нашёл — наше лобби открывается для всех (состояние `WaitingAsHost`), и раз в `SearchInterval` (4 с) лидер ищет лобби полнее нашего, пока у нас только своя пати. Переезжаем, только если там больше игроков или столько же, но ключ меньше: два ждущих хоста сходятся в одно лобби, а не меняются местами.
5. Лобби заполнилось или вышел `SearchTimeout` (60 с) — хост начинает матч. Сессия помечена «собрана поиском», и в матче пустые места занимают боты (`MatchEntryPoint`); выбор числа ботов в лобби на неё не действует.

**Хост, который ждёт игроков,** объявляет своё лобби в каталоге (`ILobbyDirectory`) и обновляет число игроков и мест. Найденных поиском пускает, только пока ждёт; иначе отказ `lobby_closed` (объявление устарело: матч уже начался). После миграции новый хост продолжает ждать с тем же сроком: состояние поиска переходит к нему вместе со слотами (`HostSeed.Matchmaking`).

**Пинг после подключения** (`MatchmadePingGuard`). Оценка до подключения бывает неточной, поэтому хост первые `PingProbeSeconds` (3 с) меряет RTT до каждого, кто пришёл по поиску, парой RPC. Если медиана выше `MaxMeasuredRttMs` (200 мс), хост отправляет его пати обратно к лидеру, а тот продолжает поиск без этого лобби. В замер входят кадры обработки на обеих сторонах (до ~2 кадров), это учтено в пределе. Друзей (вступивших в пати хоста или пришедших переездом без поиска) не проверяем.

**Каталоги лобби.**
- **Steam** (`Networking/Steam/SteamLobbyDirectory`): объявление — то же лобби Steam, что создаётся для приглашений. Пока хост ждёт, лобби публичное, в данных `tt_game`, `tt_ver`, `tt_open=1`, `tt_players`, `tt_free`, `tt_ping` (ping location хоста). Ищущий фильтрует список лобби по этим ключам (на App ID 480 список общий со всеми, поэтому `tt_game` обязателен), оценивает пинг через `SteamNetworkingUtils.EstimatePingTimeFromLocalHost` и подключается к SteamID из `tt_host`, не входя в лобби. Так игрок в каждый момент состоит в одном лобби Steam — вопрос «можно ли в двух сразу» не возникает.
- **Локальный** (`Networking/Matchmaking/LocalLobbyDirectory`, только редактор и development-сборка): копии игры на одной машине объявляют себя файлами в `Application.temporaryCachePath/local-lobbies`, адрес — 127.0.0.1 и порт хоста (`-tt-port`). Для автотеста без двух аккаунтов Steam.

Каталог выбирается по транспорту сессии: Steam — Steam, IP — локальный. В релизной сборке по IP искать негде.

**Ограничения:**
- Через Steam поиск не проверен: нужны несколько аккаунтов на разных машинах. Поведение фильтров и оценки пинга подтверждено только по исходникам Steamworks.NET.
- Часы машин расходятся: срок поиска хранится как время UTC, после миграции таймер может сдвинуться на секунды.
- Пати, пришедшая в последний момент, может получить отказ `in_match`/`lobby_closed` — тогда она собирается у лидера и ищет дальше.
- UI («Найти игру» с таймером и отменой) — шаг 5; пока консоль `net.find`.

| Поиск игры: интерфейс, логика, правила выбора, проверка пинга, каталоги лобби, состояние в сессии | `Core/Network/IMatchmaking`, `Networking/Matchmaking/MatchmakingService`, `MatchmakingRules`, `MatchmadePingGuard`, `LocalLobbyDirectory`, `Networking/Steam/SteamLobbyDirectory`, `Networking/Lobby/MatchmakingInfo` |

| Снимки состояния тел, интерполяция, история и коррекция предсказания (без правил игры) | `Networking/Sync` |
| Персонаж: симулирует хост; владелец предсказывает своё движение, остальные интерполируют | `Gameplay/Characters/PlayerCharacter`, `CharacterNetSync` |

**`PlayerSlot`** = сетевой клиент + индекс локального игрока на нём. Один клиент может занимать несколько слотов (кооп на одном экране по сети). Слот задаёт номер игрока и цвет.

## Правила для нового сетевого кода

- Новый сетевой префаб: компонент `NetworkObject`, группа Addressables своего слоя, **метка `network`**. Ссылаться на него из `NetworkManager` не нужно.
- `[Inject]` в `NetworkBehaviour` работает, если объект создан через DI: на хосте — `IObjectResolver.Instantiate`, на клиентах это делает обработчик префабов.
- `NetworkVariable` пишите в `OnNetworkSpawn` (на сервере) или позже. До `Spawn` NGO выдаёт предупреждение. Начальные значения передавайте обычными полями, как `StubCharacter.ConfigureServer`.
- Перед сменой сцены хост **деспавнит** сетевые объекты этой сцены. Если клиент уничтожит заспавненный объект вместе со сценой сам, NGO запишет ошибку.
- Обработчики событий, которые вызываются из сетевых колбэков, не должны бросать исключения: исключение прервёт применение остального сообщения NGO. `SessionLobby` изолирует подписчиков, но UI всё равно отписывается в `OnDisable`/`OnDestroy`.
- UI, который виден только хосту или только клиенту, переключает `SessionRoleVisibility` на всегда активном корне UI. Не вешайте его на саму кнопку: Unity не вызовет `OnDestroy` у объекта, который ни разу не был активен.

## Как проверить руками

1. **Tiny Tumble → Build → Windows Development** (сборка в `Builds/Dev`, папка в `.gitignore`).
2. Запустите два экземпляра `TinyTumble.exe` (или сборку + редактор).
3. В первом: «Играть». Во втором: адрес `127.0.0.1` (или LAN-IP хоста) → «Подключиться».
4. Во втором «Готов», в первом «Начать матч». Управление — таблица в `character-and-combat.md`.

Консоль (` или F1):

| Команда | Что делает |
|---|---|
| `net.host [auto\|ip\|steam]` | создать игру и перейти в лобби. `auto` (по умолчанию) — через Steam, если он запущен |
| `net.join 192.168.0.10[:7777]` | подключиться по IP |
| `net.join steam:<SteamID>` | подключиться к хосту через Steam |
| `net.invite` | открыть оверлей Steam «Пригласить друзей» (хост через Steam) |
| `net.leave` | выйти в меню (закрывает сессию) |
| `net.status` | роль, id, состояние хоста, транспорт, SteamID, пати, поиск и таймер, слоты с пати, симулятор |
| `net.party.move 192.168.0.10[:7777]` или `steam:<SteamID>` | лидер уводит всю пати к другому хосту |
| `net.party.home` | лидер уводит пати из чужой сессии к себе |
| `net.find` | найти игру (из меню или лидером своей пати в своём лобби) |
| `net.find.cancel` | прекратить поиск |
| `net.sim 60 10 2` | задержка 60 мс, джиттер 10 мс, потери 2% на отправку с этой машины; `net.sim off` |
| `net.drop 8` | полностью оборвать связь этой машины на 8 с (обе стороны). Проверка переподключения и миграции руками |

Задержка симулятора добавляется на отправку **каждой** стороной: `net.sim 60` у обоих даёт RTT около 120 мс. Симулятор работает в редакторе и development-сборках и только по IP: это слой Unity Transport.

### Через Steam

Нужны две машины с **разными** аккаунтами Steam (две копии под одним аккаунтом друг к другу через Steam не подключатся) и Steam, запущенный на обеих. Аккаунты должны быть друзьями, чтобы работало приглашение.

1. На первой: «Играть» (хост поднимется через Steam, в логе `Hosting over Steam` и `Steam lobby … is open for invites`), затем в лобби кнопка «Пригласить» (или `net.invite`) и пригласить второго. Кнопка видна хосту и клиентам, только пока сессия идёт через Steam и лобби Steam открыто.
2. На второй: принять приглашение в Steam. Если игра запущена — она войдёт в лобби Steam и подключится к хосту; если нет — Steam запустит её с `+connect_lobby <id>`, и подключение начнётся из главного меню. Без приглашения: `net.join steam:<SteamID хоста>` (SteamID пишет `net.status`).
3. Миграцию проверить так же, как по IP: хост выходит в меню посреди матча, клиент становится хостом через Steam, владение лобби Steam переходит к нему.

**Как устроены приглашения.** Хост через Steam создаёт лобби Steam «только для друзей» и пишет в его данные свой SteamID (`tt_host`) и версию протокола (`tt_ver`). Приглашённый входит в лобби, сверяет версию и подключается к `tt_host`. Лобби — только «дверь»: состав и слоты ведёт NGO-сессия. Когда хост уходит, Steam отдаёт владение лобби случайному участнику; тот передаёт его новому NGO-хосту, а новый хост переписывает `tt_host`. Код — `Networking/Steam/SteamInvites`.

## Сквозной автотест (две сборки)

Хост и клиент проходят меню → лобби → матч → итоги → лобби с виртуальной клавиатурой: клиент жмёт W, хост — D. Каждая сторона проверяет, что двигаются и свой персонаж (у клиента — предсказанный), и чужой (интерполированный). В матче есть бот, он дерётся по-настоящему; чтобы исход драки не заканчивал матч посреди проверки сети, в автотесте выпавшие всегда возрождаются. Итог — строка `[AutoTest] RESULT PASS|FAIL` в логе и код выхода 0/1.

```bash
EXE=Builds/Dev/TinyTumble.exe
$EXE -batchmode -nographics -tt-autotest host   -tt-clients 1 -logFile host.log &
$EXE -batchmode -nographics -tt-autotest client -tt-address 127.0.0.1 -logFile client.log
```

Ключи (общие для всех копий):

| Ключ | Что делает |
|---|---|
| `-tt-clients 2` | сколько клиентов в сессии; передаётся и хосту, и клиентам |
| `-tt-port 7778` | порт, на котором эта копия поднимет хост, если станет преемником. **У копий на одной машине порты должны различаться** |
| `-tt-netsim 60,10,2` | симулятор сети |
| `-tt-bots 0` | сколько ботов в матче (по умолчанию из `MatchConfig`) |
| `-tt-duration 6` | длительность матча в сценарии `full` |
| `-tt-scenario full` | по умолчанию: цикл с проверкой движения своего и чужого кубика |
| `-tt-scenario hostleave` | хост выходит в меню посреди матча; клиент становится новым хостом и сохраняет свой слот |
| `-tt-scenario hostcrash` | процесс хоста убит посреди матча (нужно 2+ клиента); первый по плану становится хостом, остальные переходят к нему, у всех прежние слоты |
| `-tt-scenario clientdrop` | у клиента на 8 с пропадает сеть посреди матча; он возвращается, досматривает матч и попадает в лобби в свой слот |
| `-tt-scenario partymove` | три копии: хост-цель, лидер пати (`-tt-party leader`, сначала сам хостит свою пати) и участник (`-tt-party member`). Пати переезжает к хосту (`-tt-target`) целиком, затем лидер уводит её к себе. Проверяется, что пати и лидер сохраняются, а у хоста-цели слоты уехавших освобождаются сразу |
| `-tt-scenario matchmake` | все копии (`-tt-clients` — сколько их всего) ищут игру локальным матчмейкером, сходятся в одно лобби, по сроку поиска (`-tt-search`, с) начинается матч, пустые места занимают боты. Проверяется, что все встретились и ботов ровно `4 − игроков` |
| `-tt-scenario steamhost` | только хост, нужен запущенный Steam: хост поднимается через Steam, лобби для приглашений открывается и в лобби видна кнопка «Пригласить», после выхода в меню лобби закрывается. В сценариях по IP хост проверяет, что кнопки не видно. Подключение второй стороны через Steam этот сценарий не проверяет (нужны два аккаунта) |

Все сценарии, кроме `steamhost`, идут по IP: автотест ставит `HostTransportPreference.Ip`, потому что копии на одной машине сидят под одним аккаунтом Steam.

Пример `partymove` на одной машине:

```bash
$EXE -batchmode -nographics -tt-autotest host   -tt-scenario partymove -logFile host.log &
$EXE -batchmode -nographics -tt-autotest client -tt-scenario partymove -tt-party leader -tt-port 7778 -tt-target 127.0.0.1:7777 -logFile leader.log &
$EXE -batchmode -nographics -tt-autotest client -tt-scenario partymove -tt-party member -tt-port 7779 -tt-address 127.0.0.1:7778 -logFile member.log
```

Пример `matchmake` на одной машине (у копий разные `-tt-port`: это их адреса в локальном каталоге):

```bash
for p in 7777 7778 7779; do
  $EXE -batchmode -nographics -tt-autotest client -tt-scenario matchmake -tt-clients 3 -tt-search 20 -tt-port $p -logFile mm$p.log &
done; wait
```

Пример `hostcrash` на одной машине:

```bash
$EXE -batchmode -nographics -tt-autotest host   -tt-clients 2 -tt-scenario hostcrash -logFile host.log &
$EXE -batchmode -nographics -tt-autotest client -tt-clients 2 -tt-scenario hostcrash -tt-port 7778 -logFile c1.log &
$EXE -batchmode -nographics -tt-autotest client -tt-clients 2 -tt-scenario hostcrash -tt-port 7779 -logFile c2.log
```

Проверено 2026-10-20 и повторно 2026-10-24 (после этапов 3–4): проходят `full` (в том числе с симулятором 60/10/2), `hostleave`, `hostcrash` (хост + 2 клиента) и `clientdrop`; в логах нет предупреждений NGO. 2026-11-13 после перехода на `SessionEndpoint` и Steam-транспорт: проходят `full`, `hostleave`, `clientdrop`, `hostcrash` (хост + 2 клиента) и `steamhost`. 2026-11-13 после пати (шаг 3): те же сценарии и `partymove` (три копии), в логах нет предупреждений NGO. 2026-11-13 после поиска игры (шаг 4): все сценарии и `matchmake` (три копии: встретились в одном лобби, матч 3 игрока + 1 бот).

## Пати и матчмейкинг (план)

*Добавлено 2026-11-13. Шаги 1–4 сделаны (см. «Порядок работ»). Пересматривает пункт «Не делать в MVP: собственный онлайн-матчмейкинг» из `coop-arena-brawl-ideas.md`: свой бэкенд по-прежнему не пишем, поиск идёт через Steam Lobbies. Решение нужно подтвердить командой и внести в роадмап.*

### Требования

- **Пати до 4 человек.** Пати из 4 сразу начинает матч, без поиска. Если людей меньше, лидер запускает поиск.
- **Играть можно и без четвёрки.** Если поиск никого не нашёл за отведённое время, матч начинается с ботами на свободных слотах. Люди добавляются между матчами вместо ботов.
- **Без заметных лагов.** Задержка важнее полного лобби: лучше сыграть с ботом, чем с игроком, у которого 250 мс. Подбор идёт по фильтру расстояния Steam, другие критерии (регион, навык) не нужны.

### Сейчас

Подключиться можно по IP хоста, через Steam по SteamID или по приглашению Steam (шаг 2). Пати отделена от сессии и переезжает между сессиями целиком (шаг 3, раздел «Пати»). «Найти игру» ищет открытые лобби, открывает своё и по сроку начинает матч с ботами (шаг 4, раздел «Поиск игры»). «В меню» выводит игрока из пати.

### Модель: «хост или присоединение»

```
Пати = Steam-лобби (только для друзей), лидер = владелец лобби и хост NGO, друзья подключены к нему по SteamID
  └─ в пати 4 человека → «Начать матч», как сейчас
  └─ меньше 4 → «Найти игру» (решает лидер):
       1. ищет публичные лобби: version == N, state == lobby, свободно ≥ размера пати, фильтр расстояния «близко»
       2. отбрасывает кандидатов с оценкой пинга до хоста выше порога (см. ниже)
       3. нашёл → пати переезжает: все подключаются к тому хосту с одним PartyId
          хост отказал (места уже заняты) → следующий кандидат
       4. не нашёл → лидер открывает своё лобби для всех и ждёт; периодически ищет лобби полнее своего и переезжает туда
          (так двое ожидающих хоста не висят в пустых лобби, не видя друг друга)
       5. время поиска вышло → матч с ботами на свободных слотах
  └─ после матча: «ещё раз» в том же лобби или «уйти с пати» (лидер снова хост своей пати)
```

Пати переезжает целиком, поэтому в каждый момент игрок состоит в одном Steam-лобби. В реализации ищущий в найденное лобби Steam не входит (только читает его данные и подключается к хосту), поэтому вопрос о двух лобби сразу не встал.

### Задержка

- **Ступени фильтра расстояния.** Сначала ищем «близко». По таймеру расширяем до «по умолчанию», дальше не идём. «Далеко» и «по всему миру» не используем.
- **Оценка пинга до подключения.** Хост публикует в данных лобби свою ping location из `ISteamNetworkingUtils`. Ищущий оценивает пинг до каждого кандидата и отбрасывает тех, кто выше порога. Порог задаётся в `SessionConfig`: стартовое значение 120 мс RTT, уточнить на плейтесте. Наша интерполяция (0.1 с) и предсказание рассчитаны на такой порядок задержки. Имена API сверены с исходниками Steamworks.NET (`GetLocalPingLocation`, `ConvertPingLocationToString`, `ParsePingLocationString`, `EstimatePingTimeFromLocalHost`); поведение на живом Steam не проверено.
- **Проверка после подключения.** Хост измеряет реальный RTT в лобби. Если медиана выше жёсткого предела, хост отправляет пати обратно к лидеру (переезд с причиной `HighPing`), и поиск продолжается. Код `high_ping` заведён для текстов UI.
- **Связь через Steam.** P2P идёт через ретрансляцию Steam (SDR), без проброса портов. Задержка через ретранслятор обычно чуть выше прямой, это учитывается порогом.
