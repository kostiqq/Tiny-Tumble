# Как работать в проекте Tiny Tumble

Короткие правила для всей команды. Если правило мешает работе, предложите правку через PR в этот файл.

## 1. Первый запуск

1. Установите **Unity 6 LTS** точной версии из `ProjectSettings/ProjectVersion.txt` (через Unity Hub). Другая версия редактора = переимпорт и мусорный diff.
2. Установите **Git LFS** и выполните `git lfs install` один раз на машине.
3. Клонируйте репозиторий и откройте папку в Unity Hub.
4. Настройте Smart Merge для сцен и префабов (один раз). В `.git/config` или глобальном конфиге:
   ```
   [merge]
       tool = unityyamlmerge
   [mergetool "unityyamlmerge"]
       trustExitCode = false
       cmd = '<путь к Unity>/Editor/Data/Tools/UnityYAMLMerge' merge -p "$BASE" "$REMOTE" "$LOCAL" "$MERGED"
   ```
5. IDE: Rider или Visual Studio с пакетом Unity. В Unity: *Preferences → External Tools* — выбрать IDE и нажать *Regenerate project files*. IDE подхватит `.editorconfig` сама.
6. Откройте сцену `Boot` и нажмите Play. Игра всегда стартует с неё.

## 2. Ветки и коммиты

- `main` всегда собирается и запускается. Прямые пуши в `main` запрещены.
- Ветки: `feature/<кратко>`, `fix/<кратко>`, `art/<кратко>`, `ui/<кратко>`, `tech/<кратко>`. Пример: `feature/grab-throw`.
- Одна ветка — одна задача. Ветка живёт не дольше нескольких дней, чтобы не копить конфликты.
- Коммиты в формате [Conventional Commits](https://www.conventionalcommits.org/ru/):
  `feat: бросок напарника`, `fix: ragdoll не встаёт на наклонной арене`, `art: модель сковородки`, `refactor: ...`, `chore: ...`.
- Перед PR подтяните свежий `main` (`git merge origin/main` или rebase своей ветки).

## 3. Pull Request

- PR небольшой: идеально до ~400 строк кода. Большую фичу режьте на части.
- В описании: что сделано, как проверить (сцена, шаги), скриншот или гифка для визуальных изменений.
- CI (сборка + EditMode-тесты) должен быть зелёным.
- Ревью: код — от второго программиста; арт и UI — от арт-директора. Автор мержит сам после одобрения.
- Сетевые изменения обязательно проверить в режиме хост + клиент (два билда или ParrelSync / Multiplayer Play Mode) и с Network Simulator.

## 4. Сцены, префабы и бинарные файлы

Unity плохо мержит сцены. Чтобы не терять работу:

- **Одну сцену одновременно редактирует один человек.** Перед правкой напишите в чат команды «беру сцену X».
- Всё, что можно, выносите в префабы. Сцена арены = набор префабов, а не ручная расстановка объектов.
- Бинарные файлы (`.fbx`, `.png`, `.psd`, `.wav` …) идут через LFS. Для `.psd` и больших исходников используйте `git lfs lock`.
- Не коммитьте: `Library/`, `Temp/`, `Logs/`, `UserSettings/`, `obj/`, `Builds/`, `*.csproj`, `*.sln` (всё уже в `.gitignore`).
- Каждый ассет коммитится вместе со своим `.meta`. Нет `.meta` — у всех сломаются ссылки.

## 5. Структура проекта

```
Assets/
  _Project/
    Scripts/
      Bootstrap/       корень композиции: LifetimeScope'ы, точка входа
      Core/            базовые типы, утилиты, без зависимостей от Unity-сервисов
      Infrastructure/  сцены, сохранения, Addressables, ввод, аудио
      Networking/      NGO: сессия, спавн, транспорт, RPC-обёртки
      Gameplay/        персонаж, бой, арены, режимы, модификаторы, ведущие
      AI/              боты и ИИ ведущих
      UI/              View и Presenter
      Editor/          инструменты редактора
      Tests/           EditMode и PlayMode тесты
    Art/  Audio/  Prefabs/  Scenes/  Configs/  AddressableAssets/
  Plugins/ и сторонние пакеты — отдельно, не правим
```

- Каждая папка в `Scripts/` — отдельный Assembly Definition. Зависимости идут только вниз: `Bootstrap → UI / AI → Gameplay → Networking → Infrastructure → Core`. `UI` и `AI` друг о друге не знают; `Bootstrap` (корень композиции с LifetimeScope'ами) — единственная сборка, которая видит всех. Обратная ссылка = ошибка архитектуры, обсудите в PR. Полный граф и список пакетов для каждой сборки: `assembly-definitions.md`.
- Пространство имён повторяет путь: `TinyTumble.Gameplay.Combat`.

## 6. Стиль кода

Форматирование и именование задаёт `.editorconfig`, IDE подсвечивает нарушения. Кратко:

| Что | Как |
|---|---|
| Типы, методы, свойства, события, константы | `PascalCase` |
| Интерфейсы | `IPlayerInput` |
| private / protected поля, включая `[SerializeField]` | `_moveSpeed` |
| private static поля | `s_instanceCount` |
| Параметры и локальные | `camelCase` |
| Скобки | с новой строки (Allman), всегда даже для одной строки |

Дополнительно:

- Поля для инспектора: `[SerializeField] private float _jumpForce;`, а не `public`.
- Магических чисел в коде нет: баланс (встряск, окна парирования, кулдауны) живёт в ScriptableObject-конфигах. Геймдизайнер меняет числа без программиста.
- Для наследников `UnityEngine.Object` **не используйте `?.` и `??`**: они не видят уничтоженные объекты. Пишите `if (target != null)`.
- Никаких `FindObjectOfType`, `GameObject.Find` и `SendMessage` в рантайме.
- Комментарии объясняют «почему», а не «что». Язык комментариев — русский, имена в коде — английские.

## 7. Архитектурные правила стека

### VContainer
- **Никаких синглтонов и статических менеджеров.** Зависимости приходят через DI.
- В обычных классах — внедрение через конструктор; в `MonoBehaviour` — через метод `[Inject] public void Construct(...)`.
- Регистрация сервисов только в `LifetimeScope` нужного уровня: `Root` (вся игра), `Scene` (меню/лобби), `Match` (один матч). Сервис матча не регистрируйте в `Root`.
- Префабы, создаваемые в рантайме, инстанцируются через `IObjectResolver.Instantiate`, иначе зависимости не внедрятся.

### R3 и MessagePipe
- Каждая подписка R3 освобождается: `.AddTo(this)` в `MonoBehaviour`, `CompositeDisposable` в обычных классах (освобождается в `Dispose`).
- `ReactiveProperty` — для состояния (счёт, встряск, таймер), MessagePipe — для разовых событий (игрок выбыл, раунд закончился).
- Не стройте игровую логику на длинных цепочках операторов; если цепочку сложно прочитать — перепишите обычным кодом.

### UniTask
- Вместо корутин — `async UniTask`. `async void` запрещён (кроме обработчиков UI-событий, и то через `.Forget()`).
- Любой долгий метод принимает `CancellationToken`; в `MonoBehaviour` используйте `destroyCancellationToken`.

### Addressables
- Ассеты контента (арены, персонажи, косметика, ведущие, звук) грузятся только через сервис загрузки, никаких прямых ссылок из кода.
- Всё, что загружено, освобождается (`Release`). Владелец загрузки = владелец освобождения.
- Новый ассет — в правильную группу и с label. Перед мержем проверьте *Addressables → Analyze*.

### Netcode for GameObjects
- **Хост авторитетен:** попадания, встряск, правила раунда, боты, ведущий решаются только на хосте. Клиент отправляет ввод и показывает мгновенный визуальный отклик.
- RPC через атрибут `[Rpc(SendTo.Server)]` / `[Rpc(SendTo.ClientsAndHost)]`, имя метода оканчивается на `Rpc`: `RequestGrabRpc`.
- `NetworkVariable` только для состояния, которое нужно опоздавшему клиенту; события — через RPC.
- Каждый сетевой префаб зарегистрирован в списке сетевых префабов и загружается до старта сессии.
- Соло тоже работает как хост: не пишите отдельную офлайн-ветку логики.

## 8. Тесты

- Логика без Unity (правила режимов, модификаторы, подсчёт очков, голосование) покрывается EditMode-тестами.
- PlayMode smoke-тест: матч с ботами от начала до конца без ошибок в консоли.
- Баг, который дошёл до `main`, сначала воспроизводим тестом, потом чиним.

## 9. Арт и UI

- Масштаб: 1 юнит = 1 метр, pivot у основания модели, ось Y вверх, экспорт FBX с применёнными трансформами.
- Нейминг: `SM_` статичные меши, `SK_` скелетные, `M_` материалы, `T_` текстуры (`T_Pan_Albedo`), `A_` анимации, `UI_` элементы интерфейса, `SFX_` / `MUS_` звук.
- Все персонажи на одном риге; новый персонаж проверяется в референсной сцене до коммита.
- UI-ассеты: исходники в LFS, в проект — экспорт нужного размера, атласы через Sprite Atlas.

## 10. Готово, если

- Фича работает в соло, в локальном коопе и по сети (хост + клиент).
- В консоли нет новых ошибок и предупреждений.
- Числа баланса вынесены в конфиги.
- CI зелёный, ревью пройдено.
- Если поменялось поведение, описанное в GDD или роадмапе, это отмечено в PR.
